## [Unreleased]

### Added

- `make test` target and a `Go` CI workflow running build / vet / gofmt / test on push and PR. The verify section had `build`, `vet` and `fmt` but no way to run the tests, and no workflow ran them at all — which matters because `TestCloudInitTreeIsASCII` is the only check that can see non-ASCII in `cloudinit/base/*` (those files are base64-encoded before injection, so the deploy-time guard structurally cannot catch them). The workflow is read-only (`permissions: contents: read`), checks out without persisting credentials, pins both actions to immutable commit SHAs (`actions/checkout` v4.4.0, `actions/setup-go` v5.6.0) so a retagged `v4`/`v5` cannot change what runs, and cancels a run superseded by a newer push to the same ref.
- `lair` group on release fleets: the lair passphrase is written `root:lair` mode `640` (was root-only `600`) so co-located non-root services (pricing-oracle, bridge-orchestrator) can read it to sign zome calls via lair without running as root.
- `doc/deploy-new-release.md` § Migration window — the version-retention policy for a migration release (released versions stay up by deliberate choice so 3–4 coexist; no auto-decommission; a fleet comes down only on a deliberate org end-of-support decision — remove its registry entry, then tear down manually; single-step climb), pointing at the version-migration `notary-host.md` § Lifecycle as the authoritative home.
- `notary` node type to release fleets (one always-on droplet per migration notary).
- `domino_cli` crate.
- `hf-swapper` and `hash-explorer` node types to release fleets.
- Server types are now defined in a `nodeTypes` registry in `main.go`; adding a type is one entry there plus its `<name>-count` / `<name>-size` keys in `defaults.yaml`.

### Changed

- `make new-release` reads `DIGITALOCEAN_TOKEN`/`INFLUX_TOKEN` from a gitignored `heart/.env` and sets `digitalocean:token` + `heart:influx-token` + `heart:project-name` on the stack itself.
- The cloud-init base-image contract — the `lair-keystore.service` + `holochain.service` systemd units and the first-boot core (lair passphrase, lair init, connection-URL discovery, conductor-config patch) — is factored into `cloudinit/base/` as the single shared source, so the local-testnet fleet image (`automation/emulation/heart/`) consumes the SAME bytes and cannot drift from prod. `main.go` reads those files and base64-injects them into the rendered cloud-config via `encoding: b64` write_files (`renderCloudInit` / `readBaseFileB64`); the fleet Dockerfile COPYs them verbatim from a `heart` build context. The InfluxDB metrics env moved out of the inlined `holochain.service` into a prod-only `holochain.service.d/10-metrics.conf` drop-in — that split is exactly what lets the metrics-less local fleet reuse the base unit unchanged. New `TestRenderCloudInit` asserts every template action resolves, the output is valid cloud-init YAML, the three base files are injected byte-identical to `cloudinit/base/`, and the InfluxDB env lives in the drop-in (not the base unit). Rendered user-data did change: besides moving the units + core from inline heredocs to b64-injected write_files, `lair-keystore.service` gained an `ExecStartPost` that waits for the lair socket and grants it to the `lair` group (`chgrp lair` + `chmod g+w`) so co-located non-root services can dial it. Run a `pulumi preview` sanity check before shipping per the deploy DoD.
- Default fleet shape shrinks to 4 droplets per release: `always-online-count` and `unyt-bridging-count` default to `0` (the service nodes each run a full conductor + agent, so dedicated always-on peers add nothing; unyt-bridging never took on its intended bridging duty) and `notary-count` defaults to `1` (single-notary policy for now — raise per release when a window needs resilience). The role types stay defined in `nodeTypes`; re-enabling one is a count bump plus restoring its parked config from `automation/config/disabled/`. Docs (`README`, `deploy-new-release`, `setup-progenitor`, `Pulumi.release.yaml.example`) updated to the 4-role fleet, including the watchtower observer now living on the hash-explorer node.
- bump cloud-init HOLOCHAIN_VERSION and holo-keyutil deps to Holochain 0.6.2-rc.0
- Deploy model is now one Pulumi stack per unyt release, namespaced by the `heart:release` config value. Holochain/keyutil versions, network endpoints (bootstrap/signal/relay/auth), InfluxDB url/org/bucket, droplet sizes and counts are all per-release config keys; their defaults live in `defaults.yaml` (edit it to change a default for all releases). See `Pulumi.release.yaml.example` and `doc/deploy-new-release.md`.
- Makefile reworked around the Pulumi per-release workflow (`make new-release RELEASE=…`, `preview`, `up`, `destroy`); dropped the dead Terraform/Vagrant targets.

### Removed

- The `alt` second-fleet hack: `createAlt` and the `*-alt-count` config keys. Use a separate release stack instead of running a parallel `alt` set.
- Dead Terraform/Vagrant-era files: `CONTRIBUTING.md` (documented a workflow that no longer exists), `services/` (conductor config now inlined in cloud-config), `scripts/test.sh` (stale, unreferenced on-node smoke test), and the obsolete `Pulumi.heart.yaml` stack.

### Fixed

- The conductor's `bootstrap_url`, `signal_url` and `relay_url` are now quoted in the cloud-init template. They are interpolated into `/etc/holochain/conductor-config.yaml` — a second YAML document nested inside the user-data as a literal block scalar, parsed by *Holochain*, not cloud-init — so a `#` or a `: ` in one of those URLs is invisible to both cloud-init's parse and the render guard, and only Holochain's parse trips, on a node that comes up with no bootstrap peer and nothing saying why. Unquoted, a `: ` in a URL made the conductor config unparseable (`mapping values are not allowed in this context`) and a leading `#` commented the value away to `null`. Config values are now screened to match — for `"`, `\`, `$`, `%` and a backtick, for leading/trailing whitespace, and for being empty at all. Every `{{ . }}` in the template lands inside double quotes, and rejecting at `make preview` what would break out of them is what keeps the quoting that carries `#` and `:` intact. Being quoted is not one guarantee, because the template interpolates into four embedded languages and each keeps its own bytes live inside the quotes: `"` closes the scalar at all four, `\` escapes at all four (bash included, before `$` `` ` `` `"` `\` or a newline, so a value ending in one eats the closing quote and the script lines after it), `$` expands in the first-boot shell **and** in `telegraf.conf` (Telegraf substitutes the environment before it parses the TOML), a backtick substitutes in the shell only, and `%` introduces a systemd specifier in `Environment=`, where an *unknown* one (`%20` from a percent-encoded URL) drops the whole assignment with only a journal line and a *known* one (`%H`, `%a`) verifies clean and rewrites the value saying nothing at all — either way holochain's metrics exporter goes wrong while telegraf, reading the same URL from TOML where `%` is inert, keeps reporting, so the two sinks disagree rather than both failing. The shell sites run as **root**, so `pulumi config set heart:auth-server 'https://x/$(…)'` previously rendered a command substitution that would execute at first boot, and a bare `${VAR}` would expand to nothing and leave the node polling a truncated URL. Whitespace is screened because quoting changed its meaning (an unquoted scalar trimmed a trailing space, a quoted one carries it to the node), and empty is the same slip with no bytes at all: an empty `heart:holochain-version` renders a release URL with a hole in it, so first-boot's `curl -f` 404s, `set -eo pipefail` kills the runcmd, and the droplet arrives with no conductor — the original outage, reached through a value that carries nothing to reject. `TestRenderCloudInitConductorURLs` renders the real template, parses the conductor config back out of it, and asserts all three URLs reach the conductor identical to the configured value (distinct per field, so a swap between the three adjacent lines is caught too — as it now is for the telegraf, metrics-drop-in and version groups in `TestRenderCloudInit`); `TestCloudInitTemplateQuotesEveryAction` holds the quoting invariant, though only the quoting — a new interpolation site means re-deriving the byte list for its language. **Rendered user-data changes**, so the replace-on-change caveat below applies to this too.
- Fleet nodes booted bare: three em-dashes in `cloudinit/cloud-config.yaml` comments (introduced by the base-image refactor) made cloud-init's YAML loader reject the user-data outright — `unacceptable character #x0080 … position 5361`, then `Failed at merging in cloud config part … empty cloud config` — so it discarded the whole config and every droplet came up with no `holochain`, `lair-keystore`, `telegraf` or `holochain-register`. That file is injected raw; only `cloudinit/base/*` is base64-encoded, which is why the em-dashes in those files were harmless. The `cloudinit/` tree is now printable-ASCII only (`TestCloudInitTreeIsASCII`), and `renderCloudInit` refuses to emit user-data cloud-init would reject: it fails at `make preview` / `make up` time naming the byte, its offset, the rendered line and a surrounding snippet, rather than shipping a config the node silently drops at boot. The guard covers C0 controls and DEL as well as non-ASCII — an ANSI escape pasted out of colourised CLI output fails the same YAML loader with `control characters are not allowed` — and it runs on the rendered output, not the template, because config values are interpolated raw. Those values are additionally screened before rendering so the common case names the key to fix (`config value 'heart:influx-org' must be printable ASCII …`) rather than an offset into the render; secrets are blanked from the snippet, which would otherwise carry `heart:influx-token` in clear text into Pulumi's error output. Config values are screened with a stricter rule than the document, which legitimately contains newlines: a value carrying one ends its scalar early and breaks the YAML around it, reaching the same whole-config-discarded outage without a single non-ASCII byte (a trailing newline from `pulumi config set --secret … < file` is the easy way in). Covered by `TestFirstUnsafeByte`, `TestFirstUnsafeValueByte`, `TestEnsureCloudInitSafe`, `TestRenderCloudInitRejectsUnsafeBytes` and `TestRenderCloudInitErrorMasksSecrets`, plus `TestCreateFleetAbortsOnUnsafeConfig`, which pins the point of the whole thing — that the guard aborts the run with zero droplets registered, rather than merely detecting. **Deploying this onto a live fleet replaces it:** rendered user-data changes, and DigitalOcean treats `userData` as replace-on-change, so `make up` on an existing stack destroys and recreates every droplet. Roll it out on a new release stack or through a migration window, not in place.
